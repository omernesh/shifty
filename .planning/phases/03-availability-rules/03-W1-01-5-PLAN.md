<objective>
Close the gap surfaced by W1-01 Tasks 0-3 + addendums 1-3: our screen JSON fixtures are accepted at write (HTTP 200) and the components are visible in the Builder UI's component tree, **but the runtime never activates the data providers** (no `/api/v2/queries/*` calls fire on screen load). Three rounds of investigation (executor's headless probe; orchestrator's published-app browser; orchestrator's role-probe + dump-screens diagnostic) have exhausted the API-only path. The remaining unknown is one or both of:

1. **A missing field on `props.dataSource`** that the runtime requires but our fixtures omit (Builder UI auto-adds when components are composed via drag-drop).
2. **A missing `_actions` array on the screen-root container** — the Builder may add a "Fetch query on load" hook that our static JSON doesn't have.
3. **A different parent-child attachment shape.** Our `_children: [...]` tree may not match what the runtime expects (e.g., it might want `_children` on a layout component, not the screen root).

Goal: get one Builder-UI-composed reference screen, diff against our fixture, identify the missing piece(s), update `SCREEN-SHAPE.md` + the fixtures, re-apply, and finally verify Layer-2 binding resolution.

Output: a working `/shift-slots` screen in the published app preview (data renders, queries fire, `{{ Current User.shiftyTenantId }}` resolves to a real UUID).
</objective>

<background>
See `.planning/phases/03-availability-rules/03-W1-01-SUMMARY.md` (3 addendums) and `tools/budibase-cli/SPIKE-BINDINGS.md` for full investigation history.

- Logging into the Builder UI shows all 3 W1-01 screens with full component trees.
- The "Shifts provider" data provider component IS configured (Data: shift-slot-list, Limit: 50).
- The Builder UI's preview iframe still renders the screen body as empty — only the navigation chrome shows.
- Network panel shows zero `/api/v2/queries/*` calls when navigating to the LIST screen.

**Why this plan is `autonomous: false`:**
The Builder UI's "+ Add screen" affordance is hover-revealed and not surfaced by the chrome-devtools MCP a11y snapshot. Manual interaction (or a Playwright session with extension installed, or a screen recording while the operator clicks through) is required to compose the reference screen.

If the user prefers, an alternative is to **export the existing Shifty App via `tools/snapshot-budibase.ps1`, manually create a reference screen in the Builder UI, snapshot again, and diff the two tarballs.** That achieves the same goal without requiring chrome-devtools to drive the "+ Add screen" button.
</background>
