<objective>
Implement the rules engine UI + handlers: 4 new shifty-plugin handlers (SeedTeamRules, UpsertRule, UpsertRuleOverride, ResetRuleOverride), the 'חוקי הצוות' tab on team_detail (Surface 10) + 'חוקים אישיים' tab on soldier_detail (Surface 11), and the comprehensive test suite — unit tests for the tightening guard, integration tests for the seed idempotence + JS↔DB enum consistency, and e2e tests for the two UI surfaces.

This plan covers RULE-01 through RULE-07 from REQUIREMENTS.md and CONTEXT D-Area-4. The tightening guard is the most subtle piece of Phase 03 business logic: a comparison function (`isTightening`) that knows the semantic shape of each rule_key — booleans, integer maxes, integer min — and rejects loosening server-side with a structured response that the UI surfaces as a persistent Alert (NOT a toast — per CONTEXT D-Area-4: 'silent ignore + UI warning showing team baseline alongside the soldier's tightening').

The seed semantics are deliberately lazy (per RESEARCH Open Question 2) — SeedTeamRules fires on rules-tab onMount when load_team_rules returns zero rows. This avoids touching Phase 02's CreateTeam handler and exploits the ON CONFLICT IGNORE idempotence. The tradeoff: a manager who never opens the rules tab has no rule rows in the DB; this is acceptable for v1 because the solver will refuse to run when rules are missing (Phase 04 concern, not Phase 03 — but documented here for orchestrator awareness).

The unit test on `isTightening` is the load-bearing correctness gate. The Phase 04 solver consumes rule_override rows as soldier-specific tightenings, so an off-by-one or sign-flipped comparison here directly breaks the solver's correctness. The integration test asserts the JS DEFAULTS constant's rule_key set is a subset of the DB CHECK enum (Risk R-03-3 sibling).

The e2e tests round out the UI contract: the team rules form renders 8 fully-populated default rules on first visit (auto-seed-on-mount), individual rule edits round-trip to DB+audit, and the soldier override tab correctly hides fairness_objective + correctly Alerts on loosening attempts.

Purpose: Managers can configure team rules; managers can apply per-soldier tightenings; the solver receives validated rule + rule_override inputs.
Output: 4 handlers + 2 page edits + 2 new blocks + 4 new test specs.
