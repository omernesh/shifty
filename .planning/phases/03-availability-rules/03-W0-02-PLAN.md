<objective>
Plumb the `tenantId` Layer-1 source so `{{ Current User.tenantId }}` resolves to a real UUID on every authenticated request to a Budibase Query. Path: declare the custom user-schema field via the Internal API (`/api/global/configs/*`); build an invite-redemption Automation via `/api/automations` that INSERTs an `app_user` row AND PATCHes the Budibase user row with the matching `tenantId` in one chain; snapshot the result; document the procedure.

Purpose: Layer 2 (`WHERE tenant_id = '{{ Current User.tenantId }}'::uuid`) is the new top defense post-pivot. Without `{{ Current User.tenantId }}` resolving to a real value, every domain-table Query returns empty (cast to `'undefined'::uuid` throws), or worse, returns rows from no tenant (cast to NULL silently filters all). This plan plumbs the value end-to-end.

**REWRITTEN 2026-05-18, post-Internal-API-spike (`55f657b`).** The previous version of this plan was `autonomous: false` and required Builder UI click-throughs. The spike (see `tools/budibase-cli/SPIKE-FINDINGS.md`) proved that the Internal API (`/api/global/configs/*`, `/api/automations`, `/api/global/users/*`) exposes the same JSON shape the Builder UI uses and is reachable via cookie auth. The rewrite uses `tools/budibase-cli/` as the authoring surface.

Output:
1. A declared `tenantId` custom user-schema field, applied via `POST /api/global/configs` mutating the singleton settings doc.
2. The admin user's `tenantId` populated with a known UUID, verified via a round-trip `GET /api/global/users/<id>` AND a Query that references `{{ Current User.tenantId }}`.
3. An Automation `InviteRedemption_PopulateTenantId` built via `POST /api/automations` with the 4-step chain described in Task 3.
4. An inaugural snapshot tarball at `budibase-exports/YYYY-MM-DD-tenantid-field.tar.gz` via `tools/snapshot-budibase.ps1` (the W0-05 wrapper).
5. Updated `BUDIBASE-CONVENTIONS.md` §3 with the resolved Internal-API procedure + a SUMMARY.md documenting per-step outcomes.

Sequencing rationale:
- W0-03 (helper bundle) is a logical predecessor — confirms the JS-code-block integration pattern works before the Automation references the bundle. The Automation in this plan doesn't actually consume a helper, but having `Shifty.<helper>` reachable from a Builder UI JS code block is the proof point that downstream Phase 3 W1+ Automations can scale.
- W0-04 (Layer-2 CI gate) consumes this plan's outputs: the two Query names (`resolveInviteCode_GetTenantId`, `insertAppUserOnInviteRedemption`) are seeded into `EXEMPT_QUERIES` of `tools/check-bb-queries.mjs`. Match the names exactly to avoid a 1-line PR adjustment later.
- W0-05 (snapshot wrapper) ships the proper tooling used by Task 4 — no inline plink/budi incantation, just `pwsh tools/snapshot-budibase.ps1 -FeatureSlug tenantid-field`.

Fallback path (per CONTEXT D-05): if Internal API mutation of the config doc fails in any task, surface the error in the SUMMARY and STOP — do not pre-build the JOIN-to-app_user-per-query fallback. The user reviews and decides.

**Where to write the custom-field declaration:**
The `customUserSchema` lives on the Budibase global config doc, exposed via `/api/global/configs`. The doc shape will be probed in Task 1 — do not assume any specific key path. The researcher's prior report names `config.customUserSchema.tenantId` as a likely path; verify empirically.

**Schemaless user docs (researcher's deeper finding):**
Budibase user docs accept arbitrary top-level fields without prior declaration. The `customUserSchema` is largely a form-rendering hint for the Builder UI's Edit User form. If `{{ Current User.tenantId }}` resolves to a value set via `PUT /api/global/users/<id>` even WITHOUT declaring the field — then declaration is technically optional. Task 2 verifies both paths empirically.

**Credentials:** `BB_EMAIL` + `BB_PASSWORD` passed as env vars to the docker probe container only. Never committed; never written to a script file.

**Why this plan is now autonomous:**
- All steps that the previous plan version required a Builder UI click for are now reachable via JSON HTTP. The spike's `BudibaseClient` is the lever.
- The only true human-required artifact in the prior plan was "screenshot the Edit User form showing the new field." That's nice-to-have, not a release blocker; replaced by an automated round-trip assertion in Task 2.
