<background>
**BUDIBASE-CONVENTIONS.md §3 procedure (paraphrased):**
1. Builder UI → Settings → Users → schema → add custom field `tenantId` (type: text/string).
2. Populated at signup/invite redemption by a Budibase Automation that INSERTs into the `app_user` table with the right `tenant_id`, AND patches the Budibase user row with the matching `tenantId`.
3. Reference in every Query body as `{{ Current User.tenantId }}` — wrap in single quotes + cast `::uuid` (e.g. `WHERE tenant_id = '{{ Current User.tenantId }}'::uuid`).
4. The Layer-2 CI gate (W0-04) verifies this pattern is present on every domain-table query.

**Caveats from §3:**
- Budibase's Public API does not expose user-schema mutation on CE — adding the `tenantId` custom field is a one-time Builder UI action, captured in the snapshot tarball.
- `{{ Current User.tenantId }}` is parameterized (not textual substitution), so SQL injection risk is bounded.

**Builder UI access from this machine:**
- Public: https://apps.nesher.co/builder (via Cloudflare Tunnel)
- LAN: http://hpg5:8080/builder (via Tailscale MagicDNS)
- First-time admin signup may still be required if no admin account exists yet. The memory note from 2026-05-17 confirms BUDIBASE_API_KEY is provisioned on hpg5 .env; that strongly suggests admin signup is done and a key is reachable, but the executor should confirm by `curl`ing the Public API once before assuming.

<task type="auto">
  <name>Task 3: Build the `InviteRedemption_PopulateTenantId` Automation</name>
  <files>(Builder UI: Automation; no git-tracked file)</files>
  <action>
    Build a Budibase Automation in the Builder UI with these properties (executor guides user click-by-click):

    Name: `InviteRedemption_PopulateTenantId`

    Trigger: "User created" (or whichever Budibase event fires on invite-code redemption — if no native event matches "invite redemption", use "User signed up" + a conditional step that checks for an invite-code in the user metadata. If neither works, document the gap in the SUMMARY and use the closest available trigger; the goal is "fires when a new user lands with an invite-code binding".)

    Steps (in order):
    1. **Resolve tenant_id from invite code.** Input: the invite-code string passed in the trigger payload. Action: query the `invite_code` Postgres table for `tenant_id` where `code = {{ trigger.inviteCode }}` AND `redeemed_at IS NULL`. Bind result to `resolvedTenantId`.
       - The Query for this step lives in the Builder UI Queries area; create it as `resolveInviteCode_GetTenantId`.
       - SQL body (NOTE: this query is a legitimate Layer-2 exemption — it CANNOT filter on `tenant_id` since the whole point is to resolve `tenant_id` from a code. The W0-04 CI gate must whitelist this query by name. W0-04 plan documents this exemption.):
         ```
         SELECT tenant_id, role, soldier_id
         FROM invite_code
         WHERE code = {{ inviteCode }}
           AND redeemed_at IS NULL
         LIMIT 1
         ```
    2. **INSERT app_user row.** Query: `insertAppUserOnInviteRedemption`. SQL body:
         ```
         INSERT INTO app_user (id, tenant_id, role, soldier_id, email, created_at)
         VALUES (
           {{ trigger.userId }}::uuid,
           {{ steps.1.resolvedTenantId }}::uuid,
           {{ steps.1.role }},
           {{ steps.1.soldier_id }}::uuid,
           {{ trigger.email }},
           NOW()
         )
         ON CONFLICT (id) DO NOTHING
         RETURNING id, tenant_id
         ```
       - This query is ALSO a legitimate Layer-2 exemption (CREATES the tenant-bound row; no filter applicable). The W0-04 plan whitelists it by name.
    3. **PATCH Budibase user row.** Use the Builder UI's "Update Row" action against the Users table. Set `tenantId` to `{{ steps.2.tenant_id }}` (a UUID string). Match on `_id` = `{{ trigger.userId }}`.
    4. **(Optional) Mark invite code redeemed.** Query: `markInviteCodeRedeemed`. SQL body:
         ```
         UPDATE invite_code
         SET redeemed_at = NOW(), redeemed_by = {{ trigger.userId }}::uuid
         WHERE code = {{ trigger.inviteCode }}
           AND tenant_id = {{ steps.1.resolvedTenantId }}::uuid
         ```
       - This query DOES filter on tenant_id (defensive — prevents a malicious actor from poisoning another tenant's invite code if step 1 somehow returned wrong data). NOT an exemption.

    Error paths: if step 1 returns zero rows (invite code invalid/already redeemed), the Automation should halt and write to a `notification_log` row of type `invite_redemption_failed` (or similar — verify the table exists; if not, just log via Budibase's built-in Automation history).

    Document the chosen Budibase trigger name + step shapes in the SUMMARY. If the executor had to substitute for any step (e.g., Budibase trigger does not natively expose `inviteCode` in the payload), record the substitution clearly.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Unauthenticated → Builder UI | Anonymous user attempts to reach Builder UI; Cloudflare Tunnel + Budibase auth required |
| Authenticated user → Public API | User with API key accesses Public API; key scope determines access |
| Invite-code holder → app_user INSERT | Anyone with a valid invite code can trigger the Automation; risk of code enumeration |
| Builder UI Automation step → Postgres | Automation queries run as `shifts` superuser (no RLS); SQL injection risk on bindings |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03W0-02-01 | Spoofing | Invite-code redemption | mitigate | Step 1 query filters `redeemed_at IS NULL`; step 4 marks code redeemed atomically; ON CONFLICT (id) DO NOTHING on app_user INSERT prevents replay |
| T-03W0-02-02 | Tampering | Automation step ordering | mitigate | Document the exact step order in SUMMARY; snapshot tarball captures it; future Automation edits gated by PR-time snapshot diff review |
| T-03W0-02-03 | Information Disclosure | `resolveInviteCode_GetTenantId` returns role/soldier_id | accept | Caller (Automation) MUST have a valid invite code; code is single-use; risk bounded to the code's lifetime |
| T-03W0-02-04 | Elevation of Privilege | Forged `userId` in Automation trigger payload | mitigate | Use Budibase-native "User created" trigger (Budibase generates userId server-side); never bind userId from request payload |
| T-03W0-02-05 | Repudiation | `tenantId` mutation on Budibase user row | accept | Builder UI captures last_modified timestamp; not append-only audit but sufficient for v1 |

</threat_model>
