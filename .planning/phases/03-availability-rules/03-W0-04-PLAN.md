<background>
**Why `tools/check-queries.mjs` is reference-only, not a port target:**
The Lowdefy-era gate parses YAML files looking for KnexRaw/KnexBuilder request blocks. It is the wrong shape for Budibase — Budibase queries live in CouchDB, not in repo YAML; the only programmatic access is the Public API. Per CONTEXT canonical_refs, `tools/check-queries.mjs` informs WHAT to match (the tenant_id filter pattern, the allowlist mechanism, the self-test concept) but the implementation is a fresh write against a different data source.

**Useful patterns from the Lowdefy gate worth carrying forward:**
- The self-test mutation harness (lines 88–128 of `tools/check-queries.mjs`) — strips tenant_id from a known-good query, runs the scanner, asserts it flags the violation. This is the load-bearing "gate is alive" assertion.
- The allowlist marker concept — `tools/check-queries.mjs` uses `-- @gsd-allow-untenanted: <reason>` inline; W0-04 uses inline `EXEMPT_QUERIES = [...]` per D-03 (which rejected file-based + marker-based mechanisms in favor of inline array for PR-visible exemption diffs).
- Defense-in-depth pattern from `runNoRlsBypassCheck()` — chained gates in one filesystem walk. Not applicable for W0-04 (the gate runs over Public API responses, not the filesystem), but the structure of a single entry point dispatching to multiple modes is reusable.

**Domain table enumeration strategy:**
The gate must keep its domain-table list current as future migrations land. Two approaches considered:
1. Hard-coded list inside `check-bb-queries.mjs`, updated by hand each migration. REJECTED — drift-prone; the gate would silently miss a new domain table.
2. **Dynamic extraction from `db/migrations/*.up.sql`** by parsing `CREATE TABLE` statements. CHOSEN. The gate scans `db/migrations/` at run-time, builds the table list, and validates queries against the current list. Tables added in `0015_*.up.sql` (future) automatically get protected on first gate run.

Exclusions from the domain-table list (these tables exist but do NOT need tenant_id filtering):
- `schema_migrations` (golang-migrate internal)
- `app_user` reads for the authenticated current user — actually these DO need tenant_id filters; the exemption is only for the INSERT path on invite-redemption.
- Auth.js tables (account, session, verification_token) — Phase 1 era; Budibase replaces these. Future migrations may DROP these; check if 0008_legacy_drop did so.
- `availability_legacy` (renamed legacy table per Phase 1 / Phase 2 boundary; dropped in 0008).

Build the exclusion list by reading 0008_legacy_drop.up.sql to see what was dropped, then computing domain_tables = (all CREATE TABLE in 0001..0014) minus (all DROP TABLE in 0001..0014) minus (auth.js + framework internals).

**Budibase Public API call shape (from BUDIBASE-CONVENTIONS.md §9):**
```
curl -H "x-budibase-api-key: $BUDIBASE_API_KEY" \
     -H "x-budibase-app-id: app_dev_<id>" \
     -H "Content-Type: application/json" \
     -X POST "http://hpg5:8080/api/public/v1/queries/search" \
     -d '{"name":""}'
```
The body `{"name":""}` returns all queries (empty filter). Each query in the response has `name`, `_id`, `datasourceId`, and `fields.sql` (the SQL body).

The `x-budibase-app-id` header requires knowing the app ID. The gate must either: (a) accept it via env var `BUDIBASE_APP_ID`; (b) fetch the list of applications first via `GET /api/public/v1/applications` and iterate; (c) require it as a CLI arg. Pick (b) — most automatable; the gate iterates all apps (in case multiple Budibase apps exist for staging vs. production) and gates queries from each.

**Self-test design (mirrors tools/check-queries.mjs --self-test):**
Since the gate reads from a live API (not the filesystem), the self-test cannot mutate a file. Instead, the self-test:
1. Constructs a synthetic query object: `{ name: 'SELFTEST_synthetic', fields: { sql: 'SELECT * FROM soldier' /* no tenant_id filter */ } }`.
2. Passes it to the in-process validator.
3. Asserts the validator returns a violation.

This proves the parser/validator logic is alive even when no live API is reachable. CI runs the self-test unconditionally; the live-API check runs only when `BUDIBASE_API_KEY` is set (so contributors without hpg5 access can still validate the gate code).

**Why no husky / .github/workflows in this repo:**
- No `.husky/` directory exists.
- No `.github/workflows/` exists.
- The Lowdefy-era `tools/check-queries.mjs` is wired into npm scripts only (`npm run test:check-queries`).
- W0-04 follows the same pattern: npm script + a documented run-it-manually expectation, with a note in the SUMMARY that a future CI provider integration is a v1.1 nice-to-have. Per the user prompt, do NOT add husky if it's not already there.
</background>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Contributor → Builder UI Query authoring | Contributor writes a query; without the gate, a missing tenant filter is a silent cross-tenant leak |
| CI provider → Public API | Gate authenticates with BUDIBASE_API_KEY to fetch queries |
| Local dev → Public API | Dev runs gate locally; key sourced from env or plink-fetched .env |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03W0-04-01 | Spoofing | EXEMPT_QUERIES bypass | mitigate | Inline whitelist is PR-diff-visible; reviewer sees every exemption addition; rejected names cannot be exempted (exact match) |
| T-03W0-04-02 | Tampering | Gate disabled or skipped | accept | Gate is opt-in (no CI provider yet); manual run is documented; risk acknowledged in SUMMARY; future CI integration closes this |
| T-03W0-04-03 | Information Disclosure | BUDIBASE_API_KEY leak | mitigate | Key never logged; env-var only; never written to test output |
| T-03W0-04-04 | Denial of Service | Gate failure blocks PR | accept | Self-test runs offline; live mode skips on unreachable API; only HTTP 401/403 (real config error) blocks |
| T-03W0-04-05 | Elevation of Privilege | Forged exemption via name collision | mitigate | EXEMPT_QUERIES is exact-match (not prefix); a new query named "resolveInviteCode_GetTenantIdEvil" is NOT exempt |
| T-03W0-04-06 | Repudiation | Gate run history | accept | npm run output is the audit trail; no CI logging yet; acceptable for v1 |

</threat_model>
