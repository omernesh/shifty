<background>
**Why screen-JSON shape is the bottleneck (Task 0 rationale):**
`GET /api/screens` returns `[]` against the current empty app (proven by SPIKE-FINDINGS.md's dump of the live state). The shape of a screen JSON document — its component tree, route declaration, role permission binding, data-source wiring — is undocumented in any external surface. The Builder UI's bundled JS contains the `saveScreen` payload constructor; reading it (or capturing one round-trip in a browser session) is the cheapest path. SCREEN-SHAPE.md is a permanent reusable artifact: W2 (planning_window screens), W3 (availability declaration UI), W4 (rules catalog) all need it.

**Why bindings might still not resolve, and why that's OK:**
SPIKE-BINDINGS.md confirmed `{{ Current User.* }}` resolves to `null` on the Builder API execute path (`POST /api/queries/<id>`). It is UNKNOWN whether the same null applies to the published-app browser runtime path — that's the load-bearing open question SPIKE-BINDINGS.md "Forward path A" identifies as the cheapest way to find out. The verification at Task 4 is the experiment. Two outcomes:
- Bindings RESOLVE in browser → W1-01 ships and the rest of Phase 3 is unblocked.
- Bindings DON'T resolve in browser → Task 4 stops with concrete failing repro; the executor opens the Forward-Path-B browser MCP spike before any further W1+ work. Cost: one wasted W1-01 run, plus the screens + queries which still satisfy the CI gate and document the shape regardless.

This plan accepts the "sunk cost" risk SPIKE-BINDINGS.md flagged because the spike already estimated the alternative (Path B) at 1-2h and Path A's sunk cost is one screen+queries (~3h of executor time) — comparable, with the benefit that Path A also produces the SCREEN-SHAPE.md artifact unconditionally.

**Why one plan with 6 tasks (not multiple plans):**
The 5 tasks the user spec'd map 1:1 to the canonical "spike → extend client → ship queries → ship screens → verify → record" pipeline. Each task creates the input the next consumes; no parallelism is possible. Splitting would require an intermediate handoff (next planner reads SCREEN-SHAPE.md and decides what to do) that adds zero value and burns extra planning context. Each individual task is small (1-3h each; ~10-20% context each); the plan as a whole is medium-weight (~6-8h, ~40-50% context if executed in one run, but the executor can checkpoint between tasks).

**Why D-08/D-09/D-10 apply specifically:**
- D-08 (CLI-first): All fixtures are git-tracked JSON applied via API. The Builder UI is touched only by the browser at Task 4 for verification — never to AUTHOR.
- D-09 (autonomous): The executor makes best-effort choices on the discretion points listed below and documents them in the SUMMARY. Genuine blockers (binding failure, screen-JSON shape unattainable) stop the run.
- D-10 (browser verification at end): Task 4 is the verification. Headless verification was explicitly ruled out by SPIKE-BINDINGS.md.
</background>

<planner_discretion>
**Calls the planner is making that the user should override before execute if disagreeable:**

1. **Team selection on slot create.** Migration 0003 requires `team_id` on `shift_slot`. Phase 2 created the admin's tenant + an org_unit tree, but the dev app currently has no UI exposure of teams. **Plan choice:** the create modal includes a `team_id` select bound to a NEW query `team-list.json` (SELECT id, name FROM org_unit WHERE tenant_id = '{{ Current User.shiftyTenantId }}'::uuid AND kind = 'team'). If the executor finds the admin has zero teams in their tenant, the modal shows an empty-state CTA "Create a team first" and submission is disabled. **Alternative:** hardcode team_id from the admin's tenant context — rejected as fragile + duplicates Phase 2 team-CRUD work that hasn't migrated. **Note:** this technically adds a 6th query fixture (`team-list.json`); the must_haves "5 new queries" line will be revised to 6 during execution — flagging so the user can confirm. (Fixture filenames in `files_modified` cover the 5 explicit shift-slot/role-tag ones; team-list is the implicit 6th, treated as in scope under D-09 best-effort.)

2. **required_role_tags multiselect behavior.** `role_tag.key` is the stable identifier; `role_tag.label` is the Hebrew display string. **Plan choice:** the multiselect displays `label` (or `key` if label is null) and stores `key` into the `shift_slot.required_role_tags TEXT[]` column. **Alternative:** store full role_tag.id UUIDs — rejected because the schema stores `TEXT[]` of keys per the Lowdefy-era `soldier.role_tags` contract (kebab-case keys), and consistency between `soldier.role_tags` and `shift_slot.required_role_tags` will matter when the solver in Phase 4 intersects them.

3. **Midnight-spanning UX.** `end_time` can be less than `start_time` legally. **Plan choice:** the form accepts both times as plain `<input type="time">` (or Budibase equivalent), and on submit, if `end_time < start_time` the screen shows a Hebrew advisory below the field ("המשמרת חוצה חצות" — "shift crosses midnight") — informational only, not blocking.
