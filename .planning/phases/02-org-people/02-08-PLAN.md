Land the CSV roster import path — the largest single piece of Phase 2 by behavior count, scope, and risk surface. Plan 02 stubbed ParseCsvAndValidate and CommitRosterImport; plan 06 proved the canonicalize + color helpers work end-to-end via the single-row form AND ran the upstream Auth.js hash spike (B3 fix — was previously deferred to this plan as Task 1, which was a sequencing bug because plan 06's InviteLater shipped the primitive before the spike validated it); this plan closes ROST-08 through ROST-13.

Two-page wizard:
- roster_import.yaml — three-step wizard on ONE page gated by `_state.wizard_step` (D-09); step indicator (Ant Steps), upload Card (step 1), editable AgGrid preview with bulk-fix toolbar (step 2), Progress bar with Resend dispatch status (step 3 — kicks off automatically on Confirm and immediately redirects to result page).
- roster_import_result.yaml — Result block per UI-SPEC §"Page 6". Variants: success (all OK), warning (partial failure with bounced invites), error (commit transaction failed entirely).

The two server-side handlers do all the heavy lifting:
- ParseCsvAndValidate (D-09 + D-12 + ROST-09 + ROST-11): decode base64 CSV, papaparse, apply canonicalizeText + canonicalizeRoleTag, pre-flight check duplicate emails + unknown teams + unknown role_tags, return per-row payload.
- CommitRosterImport (D-10 + D-11 + D-12 + ROST-10 + ROST-12 + ROST-13): one transaction for INSERTs (role_tag if new, app_user if new, soldier with canonicalized name and assigned color, membership), then Resend dispatch loop with NOTF-07 backoff and 500ms inter-call spacing (Resend free-tier 2 req/s budget), then INSERT roster_import_log summary row.

**B3 — Task 1 is now a Wave-3 RE-CONFIRMATION spike, not the first verification.** Plan 06 Task 0 (upstream gate per B3 fix) ran the Auth.js verification-token hash spike BEFORE InviteLater shipped in Wave 2. By the time this plan starts, the `sendInvite` primitive has already been validated against live `node_modules/next-auth/...` source AND smoke-tested via a magic-link click. Task 1 here is a safety-net re-run: it confirms the algorithm has not silently regressed in the Wave-3 container build, and that the cumulative single-soldier invite traffic from Wave 2 has not surfaced any drift before bulk fanout fires.

SLO interpretation for ROST-13 ("50-row CSV imports in <10 seconds"): per RESEARCH Pitfall P6, the strict reading is impossible on Resend free-tier 2 req/s (50/2 = 25s minimum). The acceptable interpretation, **documented in this plan AND in Plan 10 Test A2's docstring**, is: "DB transaction commits and the result page is reachable within 10 seconds; Resend dispatch continues async in the background with a progress bar." The CommitRosterImport handler returns as soon as the DB transaction commits + the first batch of Resend sends fires; subsequent sends run on the same request-handler thread but the page navigates away as soon as the response arrives.

**W1 — 50-row SLO is exercised at scale (was previously unenforced; W1 fix).** Plan 10 owns the at-scale exercise: Test A2 imports a generated 50-row CSV at `tests/fixtures/csv/perf-50.csv` (generated at test setup OR shipped as static fixture) and asserts the SLO interpretation with three split timing budgets:
  - `dbCommitWall < 2000ms` — measured from POST commit_roster_import to the moment the handler's DB transaction commits and returns.
  - `firstBatchWall < 8000ms` — measured from POST to the moment the first batch (~16 rows) of Resend sends complete.
  - `totalWall < 35000ms` — measured from POST to last row sent. The 35s ceiling = 50 × 500ms inter-call gap (25s) + DB commit budget (2s) + 8s buffer for retries.
The ROST-13 re-interpretation is documented in Test A2's test docstring so future maintainers don't reinstate the literal-10s reading and break the test.
