## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → API → DB | Phase-2 mutating requests will write to `role_tag` and `org_unit`; the policy `tenant_id = current_setting('app.current_tenant', true)::uuid` is the last-line-of-defense for tenant isolation. The session variable is set by the Knex `afterCreate` hook from Phase 1 (`app/plugins/shifty-auth/src/hooks/knex-tenant.js`). |
| DB superuser bypass | `shifts` Postgres role is `rolsuper=t` (Phase 1 verification). RLS can be bypassed via `SET row_security = off`. Out-of-scope for migrations themselves; enforced by `tools/check-queries.mjs --no-rls-bypass` on application code (Pitfall P13). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Spoofing (tenant_id forgery) | role_tag inserts | mitigate | `CREATE POLICY tenant_isolation ... WITH CHECK (tenant_id = current_setting('app.current_tenant', true)::uuid)` rejects any INSERT whose tenant_id doesn't match the session-scoped GUC. The application layer additionally derives `tenant_id` from `_user: tenant_id` only (enforced by plans 02 and 08). |
| T-02-02 | Information Disclosure (cross-tenant read leak) | role_tag SELECTs | mitigate | RLS USING clause filters every SELECT through `tenant_id = current_setting('app.current_tenant', true)::uuid`. Tests in plan 10 confirm cross-tenant probes return 0 rows. |
| T-02-06 | Elevation of Privilege (role escalation via role_tag manipulation) | role_tag.key | mitigate | `CHECK (key ~ '^[a-z][a-z0-9-]*$')` disallows special characters that could be confused with role names; role_tag entries are *labels*, never permission grants — RBAC matrix (PRD §8.3) maps to the four-role enum on `membership.role`, completely independent from `role_tag`. Plan 02's `canonicalizeRoleTag` enforces the same byte-equal regex client-side. |

</threat_model>
